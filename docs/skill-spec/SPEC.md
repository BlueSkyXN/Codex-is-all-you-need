## 1. Skill 是什么

### 1.1 定义与组成

**Skill 是一个可发现、按需加载的任务能力包**：用指令说明某类任务何时处理、怎样处理以及何时完成，并按需携带执行所用的资源。

一个 Skill 的基本组成是：

```text
一个目录 + 一个 SKILL.md 主文件 + 零个或多个辅助文件
```

- **主文件**定义调用身份、适用任务、执行方法与完成条件。
- **辅助文件**提供详细规则、示例、脚本、模板或其他任务资源。
- **运行时**负责发现和加载 Skill，并提供模型、工具、权限与执行环境。

Skill 可以描述顺序流程、一组相关操作、判断规则或产物生成方法。只有背景资料、没有说明如何将资料用于任务的包，还没有形成完整的 Skill。

### 1.2 与相邻概念的区别

| 概念 | 主要回答 | 与 Skill 的关系 |
|---|---|---|
| Skill | 这类任务怎样完成 | 本规范的编写单元 |
| Tool / API / CLI | 某个动作怎样被程序调用 | Skill 可以使用的执行能力；接口参数由工具定义 |
| Agent / 角色 | 谁在什么上下文、权限和职责下工作 | 可以选择并执行多个 Skill |
| Plugin / 分发包 | 怎样把能力安装给使用者 | 可以装载一个或多个 Skill 及其他组件 |
| 项目指令 | 在这个项目中始终遵守什么 | 对项目持续生效，可约束 Skill 的使用 |
| 知识库 / 数据源 | 任务事实与资料在哪里 | Skill 说明怎样查询和使用，资料按自身权限维护 |

一个 Skill 不因带脚本就变成独立应用，也不因被 Plugin 包装就改变其主文件格式。

### 1.3 三层加载模型

| 层 | 通常何时读取 | 内容 | 编写重点 |
|---|---|---|---|
| L1 发现层 | 发现或列出 Skill 时 | `name`、`description` | 准确表达任务范围，关键信息前置 |
| L2 执行层 | Skill 被选中后 | `SKILL.md` 正文 | 能据此选择路线、执行任务并检查完成 |
| L3 资源层 | 执行到相关步骤时 | 辅助文件 | 只读当前步骤需要的部分 |

实际可见性还受运行时启用状态、调用策略和上下文预算影响。`description` 应写清任务语义；正文应保留主流程；长细则与大资源按需引用。脚本可以直接执行，模板可以直接复制或填充，不要求先把所有资源全文读入上下文。

## 2. 类型与设计选择

### 2.1 分开四个分类维度

以下分类用于设计，不要求增加 `type` 字段，也不构成等级或升级路线。

| 维度 | 可选形态 | 区分依据 |
|---|---|---|
| **文件形态** | 单文件 / 多文件资源包 | 完成任务是否需要 `SKILL.md` 以外的文件 |
| **任务路线** | 单路线 / 多路线（套件） | 是否需要按输入或意图选择不同执行分支 |
| **实现方式** | 指令执行 / 脚本辅助 / 外部工具集成 | 哪些环节交给模型、确定性代码或外部服务 |
| **组织范围** | 单个 Skill / 多个独立 Skill / 可选 Router | 是否存在可独立发现、执行和维护的任务边界 |

这些维度可以组合。例如，多路线 Skill 可以只用一个文件；带脚本的资源包也可以只有一条路线。多个 Skill 组成的“群”属于多包组织，不是比多文件包更高一级的单包形态。

### 2.2 按任务选择正文设计

| 设计类型 | 核心特点 | 正文应突出 | 适用例子 |
|---|---|---|---|
| **流程型** | 有前后依赖的步骤 | 顺序、前置条件、分支、停止点和完成条件 | 材料整理 → 核对 → 生成周报 |
| **操作集合型** | 同一对象上的多种相关操作 | 路线选择、每种操作的输入与输出 | PDF 提取、填表、合并 |
| **规则／评审型** | 对输入应用规则并作出判断 | 判断顺序、标准、证据要求和结果格式 | 按写作规范评审一篇文章 |
| **产物／模板型** | 生成结构稳定的交付物 | 输入字段、模板填充、内容约束和质量检查 | 会议纪要、分析报告 |
| **路由型** | 在多个独立 Skill 中选用合适能力 | 选择条件、调用前置、交接与结果汇总 | 写作任务入口选择周报或文稿评审 |

同一 Skill 可以组合设计类型，但应有清晰主线。例如，模板型可以用顺序流程生成产物；规则型可以针对不同输入设置多条路线。分类帮助组织内容，不要求为每一种类型创建一个包。

### 2.3 选择文件形态与实现方式

| 当前需要 | 选择 | 不需要额外增加什么 |
|---|---|---|
| 短指令足以完成任务，没有配套材料 | 单文件 | 不预建资源目录或脚本 |
| 有按需查阅的长规则、契约或案例 | 多文件包，增加对应资源 | 不因文件变多就拆成多个 Skill |
| 有重复、确定性或容易出错的计算／转换 | 加入脚本 | 不把全部判断强行改成代码 |
| 需要数据库、在线文档或外部系统操作 | 在流程中调用现有工具 | 不因列出依赖就自动安装或扩大权限 |
| 同一任务族有不同输入或操作 | 多路线 | 不必增加子 Skill 或额外目录 |
| 不同任务可独立触发、执行与维护 | 拆为平级 Skill | 不用一个很长的 description 勉强包住所有任务 |

优先从能完整完成任务的最小形态开始。仅在真实材料或执行需要出现时增加结构；无需为了看起来完整而增加 adapter、manifest、脚本或评测目录。

### 2.4 单路线、多路线和多包的关键区别

| 方案 | 发现入口 | 执行边界 | 选择条件 |
|---|---|---|---|
| 单路线 Skill | 一个 `name` / `description` | 一条主流程，可有异常分支 | 输入和目标基本一致 |
| 多路线 Skill | 仍只有一个入口 | 同一任务族的多条完整路线 | 用户通常把它们视为同一类能力，能自然写入同一条 description |
| 多个独立 Skill | 各自有入口 | 每包独立完成自己的任务 | 各任务有独立输入、输出或复用需求 |
| Router + 多个 Skill | Router 引导，叶子仍独立 | Router 选路与交接，叶子执行 | 多入口选择已经反复出错，单靠 description 和目录索引不够 |

“同一任务族”看任务对象、使用入口和输出目的是否相关。例如“PDF 提取／填表／合并”可用多路线；“生成周报／初始化数据库”应拆包。一个工作流的准备、执行、检查通常仍是一包中的步骤，不能仅因分成 Phase 1～N 就拆成多个 Skill。

## 3. 包、目录与文件规范

### 3.1 最小包与资源包

最小包：

```text
weekly-report/
└── SKILL.md
```

按需扩展的资源包：

```text
meeting-minutes/
├── SKILL.md                 # 必须：唯一主文件
├── references/              # 可选：详细规则、协议与契约
├── examples/                # 可选：输入输出示例、正反例
├── scripts/                 # 可选：可执行辅助代码
├── assets/                  # 可选：模板、图片和其他静态资源
├── evals/                   # 可选：作者使用的回归材料
├── <平台适配文件>             # 可选：按目标平台的位置与格式要求
└── README.md / LICENSE*     # 可选：分发与许可说明
```

`references/`、`scripts/`、`assets/` 是开放标准推荐的可选目录；`examples/`、`evals/` 是本规范的工程分工。上图展示可选位置，不要求把所有目录创建出来。需要随包携带轻量治理记录时，另见附录 A。

### 3.2 命名与边界

1. **必须**有且仅有一个作为本包入口的 `SKILL.md`；文件名区分大小写。辅助目录不得嵌套另一个可发现的 `SKILL.md`，独立 Skill 使用平级目录。
2. 目录名与 frontmatter 的 `name` **必须**一致，长度为 1～64 字符。本规范为跨平台一致性采用小写 ASCII 字母、数字与连字符，正则为 `^[a-z0-9]+(?:-[a-z0-9]+)*$`；目标平台有更小上限时按其约束。
3. 64 字符是开放标准上限；ASCII 命名是本规范的工程约定。人类可读的中文名称可以写在正文一级标题。
4. 辅助文件使用语义名，例如 `output-contract.md`、`report-good.md`、`validate_output.py`；避免用临时编号或日期代替材料用途。
5. **禁止**预建空目录、包内版本目录和占位资源。版本由治理记录表达；需要并存的独立大版本可使用平级新包。
6. 新增顶层目录必须有现有目录覆盖不了的职责。历史包或外部包的既有结构按实际用途评审，不因目录名不同就整体重写。

### 3.3 文件格式

| 文件 | 格式与要求 |
|---|---|
| `SKILL.md` | UTF-8 文本；开头是 YAML frontmatter，随后是 Markdown 正文 |
| 规则、参考与示例文档 | 通常使用 `.md`；需要机器消费时可用明确约定的 `.json`、`.yaml`、`.csv` 等 |
| 脚本 | 使用目标环境支持的语言与扩展名；在调用处说明解释器、依赖和参数 |
| 输出模板 | 使用最终产物需要的格式，如 `.md`、`.docx`、`.xlsx`；二进制模板不作为正文阅读指令 |
| 结构化数据 | 说明字段、类型和必要单位；JSON 必须合法，YAML 使用正确缩进，CSV 明确表头与编码 |
| 平台适配文件 | 文件名、位置与 schema 按目标平台定义，不自行套用其他平台字段 |

文本文件建议统一使用 UTF-8 无 BOM 和 LF 换行。代码块语言标记应与内容一致。包内资源使用相对路径，不写作者机器上的绝对路径。

## 4. SKILL.md 文件格式

### 4.1 文件整体形状

```markdown
---
name: weekly-report
description: 将一周工作记录整理为周报，适用于已有任务进度、完成事项和风险记录需要归纳成稿的场景。
---

# 周报整理

## 输入
需要一周内的工作记录；缺少关键材料时先列出缺口。

## 工作流
1. 按完成、进行中、下周计划与风险分类。
2. 合并重复记录，保留输入中的事实与数据。
3. 输出四栏 Markdown 周报，并核对每项均有输入依据。

## 完成条件
四栏齐全；无内容的栏写“无”；没有补造事实。
```

第一行 **必须**是 `---`，结束分隔行也为 `---`。frontmatter **必须**是 YAML mapping，正文从结束分隔行之后开始。分隔行前不放标题、说明或代码围栏；上例外围的 Markdown 代码围栏不属于实际文件内容。

### 4.2 Frontmatter 字段

| 字段 | 是否必需 | 内容与限制 |
|---|---|---|
| `name` | 必须 | 稳定调用身份；与目录名一致，命名规则见 3.2 |
| `description` | 必须 | 非空字符串，1～1024 字符；说明做什么以及适用任务 |
| `license` | 可选 | 许可名称或包内许可文件引用；随仓库／分发包已有明确许可时可省略重复声明 |
| `compatibility` | 可选 | 非空时不超过 500 字符；说明产品、系统依赖或网络等环境要求 |
| `metadata` | 可选 | 自定义字符串键值映射；治理用途见 11.1 |
| `allowed-tools` | 可选、实验性 | 开放标准描述为空格分隔的工具字符串；实际支持和权限语义取决于运行时 |

只有 `name` 和 `description` 是可移植必填字段。平台私有字段、脚本参数和宿主工具参数不属于这个通用字段表；平台特点见第 9 章。

YAML 写法要求：

- 缩进使用空格，不用 Tab；同一层级不得重复定义相同键。
- `name`、`description` 必须解析为字符串，不能写成数组或对象。
- 本规范采用单个物理行的 `description`，不使用 `>`、`|` 等块标量；这是工程约定。
- 值含有可能被 YAML 解释为结构的字符时使用引号，例如 `description: "整理 status: done 的工作记录，适用于按状态生成摘要的场景。"`。
- 版本和日期等治理值使用引号，例如 `version: "0.1"`、`updated: "2026-09-16"`，避免被解析为数字或日期对象。

### 4.3 Description 怎样写

采用“**做什么 + 适用于什么任务、事件或输入状态**”的句式。任务范围在发现层就应可判断，不能只放在正文。

| 写法 | 示例 | 判断 |
|---|---|---|
| 过于宽泛 | `帮助处理各种工作，提高效率。` | 看不出任务对象和何时选用 |
| 只有动作 | `生成周报。` | 缺少输入与使用场景 |
| 任务边界明确 | `将一周工作记录整理为结构化周报，适用于已有任务进度、完成事项和风险记录需要归纳成稿的场景。` | 可用于发现与选择 |

建议保持简短，通常 100～200 字已足够，任务简单时可更短。关键能力与输入条件前置；语言跟随目标读者，产品名、API 与代码标识符保留原文。不要用堆积口令和猜测用户问法代替任务语义。

两个 Skill 职责确实重叠时，可以补最小排除说明。修改 description 后，用应选中与不应选中的代表任务验证边界。

## 5. 正文章节结构与写法

### 5.1 必须表达的信息

章节名称可以调整，以下信息必须能从正文中找到：

| 信息 | 应回答的问题 |
|---|---|
| 输入与前置 | 有什么材料、环境或权限才能开始；缺失时怎么办 |
| 执行方法 | 采用什么步骤、判断规则或操作路线 |
| 输出与完成 | 交付什么；依据什么确认任务完成 |
| 异常与边界 | 不确定、失败或存在副作用时如何处理 |
| 资源用法（有资源时） | 哪一步读取、执行或使用哪个文件 |

一份短 Skill 可以用几段文字完成，不必为了章节齐全拆成空标题。主文件必须足以指导执行，不能只剩资源链接。

### 5.2 推荐章节骨架

```markdown
# 人类可读名称

## 输入与前置
所需材料、环境和开始条件。

## 工作流
有顺序的步骤，或先选路线再执行；在使用点引用资源。

## 输出与完成条件
交付物格式，以及可检查的完成标准。

## 异常与边界
缺失输入、无法继续、失败和副作用的处理方式。
```

路线选择、检查清单、工具使用、示例和参考索引均可按需要增加。文件开头的 YAML 字段负责发现，正文标题负责阅读结构，二者不互相替代。

### 5.3 不同设计类型怎样调整章节

| 类型 | 建议正文顺序 | 核心检查 |
|---|---|---|
| 流程型 | 输入 → 前置检查 → 顺序步骤 → 输出 → 异常 | 步骤有依赖关系，失败时知道停在哪里 |
| 操作集合型 | 输入 → 路线选择 → 每条操作 → 各自完成条件 | 条件可区分，每条路线可单独执行 |
| 规则／评审型 | 评审对象 → 判断顺序 → 规则 → 证据与结果 | 能从规则得出可解释判断，不能只列背景知识 |
| 产物／模板型 | 输入字段 → 模板选择 → 填充方法 → 质量检查 | 模板里的每个必需字段有来源或缺失处理 |
| 路由型 | 意图判断 → 可用性检查 → 路由表 → 交接与汇总 | 选择目标后继续完成用户任务 |

### 5.4 步骤、分支与约束

1. 用明确动作编写步骤，例如“读取输入”“核对字段”“生成报告”；写清依赖的材料与执行后的结果。
2. 决策分支应包含条件、动作和回到主流程的位置。多路线包必须先说明选路规则。
3. 完成条件使用可观察结果，例如“输出四个指定章节”“每条结论有来源”；避免只写“高质量”“尽量完整”。
4. 多种方法均可完成的环节给选择原则；脆弱或不可逆的环节才规定精确顺序。关键硬约束说明理由。
5. 外部写入、发布或删除等步骤写清前置检查、授权与失败处理；依赖声明本身不构成安装、授权或写入许可。
6. 只写执行者缺少的具体知识。长细则移到辅助文件，并在正文留下使用时机；正文建议控制在数百行内。

## 6. 辅助文件与引用

### 6.1 各目录的关键区别

| 目录 | 主要用途 | 不应替代 |
|---|---|---|
| `references/` | 详细规则、字段定义、协议、契约、排查说明 | 主文件中的任务流程 |
| `examples/` | 让执行者看到输入输出形状、正反例 | 唯一的硬规则来源 |
| `scripts/` | 执行确定性、重复或易错操作 | 必须由使用者决定的业务取舍 |
| `assets/` | 供生成产物复制、填充或加工的模板与静态资源 | 解释如何操作的说明文档 |
| `evals/` | 作者或 CI 使用的触发与结果回归材料 | 日常任务运行手册 |

同一事实只保留一份规则真源。示例展示规则如何落地，评测检查可观察结果。`evals/` 不作为任务执行依赖；目录名本身不阻止工具访问文件。

### 6.2 辅助文档怎样写

一个辅助文档围绕一个主题，至少说明用途、适用条件和具体规则；较长时增加目录或定位线索。字段契约说明必需性、类型、单位和缺失处理；示例明确标注为示例，避免被当作真实输入。

主文件在使用点引用，例如：

```markdown
生成报告前，读取 [输出契约](references/output-contract.md)，按其中的字段定义组织结果。
需要核对结果形状时，再查看 [合格示例](examples/report-good.md)。
```

链接相对于写链接的文件解析：`SKILL.md` 中的路径从包根开始；辅助文档中的相对链接从该文档所在目录开始。主文件直接指向主要资源，避免层层跳转。所有实际引用必须指向存在的资源；不要为将来可能创建的文件预先放链接。

### 6.3 脚本、模板与结构化文件

调用脚本时，主文件或对应参考文档必须说明：用途、解释器与依赖、参数、输入输出位置、失败信号和副作用。新增或修改脚本应完成与风险相称的代表性执行；没有脚本的 Skill 不为形式新增测试框架。

使用模板时，说明哪些内容是固定结构、哪些是待填字段、缺失信息怎样表示，以及产物保存在哪里。真实模板放在 `assets/`，完整示范结果放在 `examples/`。

使用 JSON、YAML、CSV 等结构化文件时，消费方必须知道其 schema 或字段契约；不要让执行者从几个示例值猜字段含义。

### 6.4 包内与包外的选择

与流程一起维护、随包分发的规则和资源可放包内。独立更新、多包共享或权限不同的中央资料放包外，包内写明怎样取得、何时使用和不可用时的处理方式。材料篇幅长时先判断是否适合拆成聚焦的参考文件，不仅凭字数将其移出包。

不得复制中央知识或外部 Skill 正文形成第二真源。调用外部 Skill 时说明稳定名称、前置条件、传入内容、期望结果与失败处理。敏感材料边界见 10.3，内部私有案例另须满足附录 B。

## 7. 标准示例

以下三个示例分别展示单文件、多文件和多路线。示例包中的路径与文件内容在本章成组给出；代码围栏不属于落盘文件。

### 7.1 单文件：流程型周报

目录：`weekly-report/SKILL.md`。

```markdown
---
name: weekly-report
description: 将一周工作记录整理为结构化周报，适用于已有任务进度、完成事项和风险记录需要归纳成稿的场景。
---

# 周报整理

## 输入与前置
使用用户提供的一周工作记录；若未提供材料，先请求记录和报告周期。

## 工作流
1. 提取已完成事项、进行中任务、下周计划和风险；合并重复记录。
2. 保留输入中的事实、数字和日期，不把计划写成已经完成。
3. 按“本周完成／进行中／下周计划／风险与求助”四栏输出 Markdown。
4. 逐条对照输入；删除无法追溯的断言，缺少的信息标记“待确认”。

## 完成条件
- 四栏齐全；确认无内容的栏写“无”。
- 每条记录有输入依据，状态与时间没有混淆。

## 异常与边界
材料相互冲突时列出冲突并请求确认；不编造工作事项或量化结果。
```

这里无需资源目录、脚本或平台 adapter。

### 7.2 多文件：模板型会议纪要

```text
meeting-minutes/
├── SKILL.md
├── references/
│   └── output-contract.md
└── assets/
    └── minutes-template.md
```

`SKILL.md`：

```markdown
---
name: meeting-minutes
description: 将会议记录整理为包含结论、行动项和待确认事项的纪要，适用于已有逐字稿或会议笔记需要形成书面记录的场景。
---

# 会议纪要

## 输入与前置
需要会议笔记或逐字稿；会议名称和日期缺失时保留为待确认。

## 工作流
1. 读取 [输出契约](references/output-contract.md)，明确各章节与行动项字段。
2. 从输入中提取已达成的结论、承诺执行的行动和未解决的问题。
3. 使用 [纪要模板](assets/minutes-template.md) 组织内容，保留输入中的责任人与日期。
4. 将结论和行动逐条回查原始记录，按输出契约处理缺失或冲突。

## 完成条件
输出 Markdown 纪要，模板章节齐全，行动项字段完整或标为待确认。

## 异常与边界
缺少原始记录时先请求材料；没有明确达成的事项不得写成会议决议。
```

`references/output-contract.md`：

```markdown
# 纪要输出契约

用于主文件的内容提取和最终核对。

- 基本信息包含会议名称与日期，缺失时写“待确认”。
- 结论只记录输入明确达成的事项；无法确认共识的内容放“待确认事项”。
- 每条行动项包含事项、责任人、截止日期；后两项缺失时写“待确认”。
- 不以建议、讨论或可能性推断出已承诺的行动。
- 确认没有内容的章节写“无”，保留章节标题。
```

`assets/minutes-template.md`：

```markdown
# {{会议名称}} 会议纪要

日期：{{会议日期}}

## 结论
{{已达成的结论}}

## 行动项
| 事项 | 责任人 | 截止日期 |
|---|---|---|

## 待确认事项
{{未解决或存在冲突的问题}}
```

主文件说明流程，参考文件定义规则，模板定义产物形状；三个文件职责不同。

### 7.3 多路线：操作集合型文稿评审

目录：`text-review/SKILL.md`。本例有两条路线，仍然只需一个主文件。

```markdown
---
name: text-review
description: 校对或评审已有文稿，适用于检查文字表达、事实表述一致性或文章结构与论证连贯性的场景。
---

# 文稿评审

## 输入
需要待评审文稿；受众和用途未说明时，仅按文中可见信息判断。

## 路线选择
- 检查错字、病句、术语和表达一致性：走“文字校对”。
- 检查章节组织、论证或信息顺序：走“结构评审”。
- 两种目标都有：先结构评审，再对保留的内容做文字校对。
- 未指定目标：默认做文字校对，并说明采用的范围。

## 文字校对
1. 检查错字、病句、术语和数字表述的一致性。
2. 按“原句／建议修改／理由”列出问题；不改变原有事实与立场。

## 结构评审
1. 识别文稿主张、支持材料和章节关系。
2. 按“位置／问题／影响／调整建议”列出断层、重复和顺序问题。

## 完成条件
注明采用的路线；每条意见有原文依据；未发现相应问题时直接说明。

## 异常与边界
外部事实无法从材料核实时标记“待核实”，不得把猜测写成确定错误。
```

多路线的关键是选择条件与各自流程；文件数量不决定路线数量。


### 8.2 Router 与调用约定

Router 负责识别任务、检查目标 Skill 可用性、选择并交接，不复制叶子的完整流程。用户要结果时，选择目标后继续执行与汇总；目标不可用时说明缺失和下一步。

Skill 之间的调用要说明：

```markdown
需要评审最终文稿时，使用 `text-review`：
- 前置：该 Skill 已可用；否则说明缺失，不声称已经完成评审。
- 传入：待评审文稿、目标受众与评审范围。
- 期望返回：带原文位置的问题和修改建议。
- 返回后：核对建议并继续整理最终交付物。
```

此处是任务交接约定；实际调用语法由运行时提供。多包协作仍应保留一份规则真源，公共资料通过稳定引用共享。

## 9. 平台特点与适配

平台差异主要发生在发现目录、显式调用方式、UI 展示、工具权限、管理元信息和分发方式。`SKILL.md` 的可移植底座与这些扩展分别维护。

| 平台 | 代表性特点 | 编写时的处理 |
|---|---|---|
| Codex | 可使用 `agents/openai.yaml` 承载展示、调用策略与工具依赖 | 正文保持可移植，平台配置按需放 sidecar |
| Claude Code / CodeBuddy | 在 frontmatter 中扩展调用与执行控制 | 只添加目标运行时支持且任务需要的字段 |
| OpenClaw | 使用厂商命名空间描述运行环境和集成要求 | 区分通用 metadata 与厂商消费的结构 |
| WorkBuddy | 创建指南、辅助脚本和宿主管理工具具有不同接口 | 按所用接口核实要求，不从模板字段推断所有链路都生效 |
| Qoder / QoderWork | CLI Skill 与界面中的角色或分发包属于不同层 | 先确定正在编写单个 Skill 还是分发包 |
| Copilot CLI | Skill、Agent 和 Plugin 各有独立载体 | 按 Skill 接口编写，避免混入其他载体的配置 |

适配规则：

1. 仅为实际目标平台增加必要扩展；产品字段不作为所有 Skill 的必填项。
2. 保持目录、调用身份、展示名和市场管理身份的区别；人类可读名称默认写 Markdown 标题。
3. 分别验证声称支持的发现、展示、调用和管理效果；文件存在、解析器读取和功能生效是不同证据。
4. 调用控制不能代替工具权限或操作授权。字段位置、类型与语义以目标平台为准。
5. 具体版本、字段完整表、安装路径、脚本参数和验证记录放在平台参考材料中；本章只保留设计特点与适配原则。

## 10. 创建流程与验收

### 10.1 从需求到标准文件

1. **确定任务边界**：写出输入、目标产物和完成条件；判断是否存在独立任务需要拆包。
2. **选择类型**：分别确定文件形态、任务路线、实现方式和组织范围；不要把这四个问题混成一个等级。
3. **先写主文件**：填写 `name`、`description`，再写输入、执行方法、输出与异常处理。
4. **按需拆资源**：将真实存在的长规则、示例、脚本和模板放到对应目录，在使用点引用。
5. **检查并试用**：检查格式和引用；用代表性任务验证能否进入正确路线、得到约定输出。
6. **处理交付需要**：仅在实际分发或协作时补治理信息、平台适配与发布检查。

### 10.2 最小合格清单

- [ ] 目录名与 `name` 一致，主文件名为 `SKILL.md`，没有嵌套的独立 Skill。
- [ ] frontmatter 是合法 YAML；必需字段为非空字符串，长度与命名符合第 3～4 章。
- [ ] description 说明能力与适用任务，未将选择条件仅写在正文。
- [ ] 正文包含输入、执行方法、输出、完成条件和必要的异常处理。
- [ ] 多路线有选路条件，每条路线都有可观察结果。
- [ ] 辅助文件有独立用途、读取或执行时机明确，实际引用可达。
- [ ] 无空目录、未完成的说明占位、作者机器绝对路径或无用生成物；模板的待填字段有填充规则。
- [ ] 有脚本时，接口与副作用有说明，并完成代表性执行验证。
- [ ] 有平台适配时，验证与声称支持的功能对应。
- [ ] 有协作或分发时，完成对应治理与材料边界检查。

不涉及的项目记为“不适用”，不为通过清单添加材料。正文格式正确后，还应检查任务是否能完成；格式检查不能代替行为检查。

### 10.3 试用与发布边界

选择一条正常任务，检查是否得到预期结果；对边界容易混淆的 Skill 增加“不应触发”或异常任务。出现触发回归、复杂流程或高风险行为时，再建立 `evals/`，必要时与无 Skill 或旧版对照。

复杂行为可用不知情的新会话验证：只给真实任务与原始材料，不泄露预期答案、诊断或修复意图。普通修改不为形式增加评测框架。

发布前必须检查：

- 包内不含密钥、凭据、访问 token、原始报告、完整附件或原始导出；公开边界不含可识别个人／客户数据及内网地址。内部私有案例必须满足附录 B。
- 脚本行为与声明一致，不执行未声明的外发、上传或删除操作，不指示绕过运行时安全机制。
- 分发许可明确；不提交缓存、系统垃圾和无用生成物。外部 Skill 在引入前应通读主文件与脚本。
- 包体积、文件类型和安装结构符合实际目标平台；打包成功不等于行为验证完成。

## 11. 版本、协作与分发

### 11.1 可选场景与版本契约

个人自用可只保留两个必需字段。采用本规范进行多人协作或公开发布时，使用下列治理字段；目标项目已有明确契约时遵循项目契约，不叠加重复字段。

```yaml
metadata:
  version: "0.1"
  updated: "2026-09-16"
  maintainer: "Alice"
  updated_by: "Alice, Bob"
```

`version`、`updated` 在上述默认治理场景中必须维护；`maintainer` 与 `updated_by` 在需要随文件记录责任时填写。前者表示当前人类负责人或稳定团队，后者表示形成当前行为版本的人类修改人；多人用英文逗号加一个空格分隔，不记录 AI、formatter 或 CI。原始作者与历史贡献由 Git / PR 保留，不另设重复的 `author` 字段。

本节是本规范的协作治理约定，不是 Agent Skills 开放标准对所有个人 Skill 的强制版本格式；目标仓库已有版本契约时以更具体的仓库规则为准。

1. `metadata.version` 是**两段式字符串**（`主.次`，字符串序列而非十进制数），首个实质状态为 `"0.1"`。
2. 主段仍为 `0` 时表示 Skill 处于初始开发或未声明稳定契约；下一次实质状态统一递增次段，例如 `0.1 -> 0.2`、`0.9 -> 0.10`。此阶段即使调整调用名、输入输出或脚本 CLI，也不自动跳到 `1.0`。
3. `1.0` 表示由负责人明确声明首个稳定公开契约，不表示“改动很大”或“质量提升很多”；未作稳定性决定、尚未发布或未被外部消费的 Skill 不得只因一次不兼容修改自动升到 `1.0`。
4. 已进入 `1.x` 及以上稳定阶段后，向后兼容的实质变化递增次段（`1.0 -> 1.1`），破坏公开调用名、必需输入输出契约、产物 schema、脚本 CLI、核心默认流程或其他 Skill 消费契约时递增主段并归零（`1.4 -> 2.0`）。
5. **同一未发布修改批次只升版一次**：短时间内的连续编辑、同一任务中的多轮修订、同一 PR 内的多个 commit、review 后继续收紧，以及文档/实现尚未形成新发布基线前的调整，都合并为一个实质状态。禁止每修改一次就叠加一个小版本。
6. 只有前一版本已经发布、合并为正式基线或被外部消费后，后续新的实质变化才开始下一次升版。时间间隔短本身不要求连续升版，发布/基线边界才决定是否形成新版本。
7. 纯排版、拼写、镜像同步、纯治理或纯展示字段变更、测试记录或维护人调整不升行为版本。同一批次最终若没有实质行为变化，也不升版。
8. **实质内容**（版本指纹范围）= `SKILL.md` 全文（仅排除纯治理和纯展示字段）+ `references/` + `scripts/` + `assets/` + `examples/` + 平台 adapter 中会改变调用、工具、依赖、宿主管理或执行行为的字段。`name`、`description`、调用策略、工具依赖和默认调用提示词必须计入，不因位于 frontmatter、`metadata` 或 sidecar 中而排除。`skill-manifest.json`、`README*`、`LICENSE*`、`evals/`、系统垃圾、治理字段，以及仅用于展示的名称、简介、图标和品牌色不算实质变更。
9. `metadata.updated` 取该实质修改批次形成最终状态的 Git committer date（`YYYY-MM-DD`）；尚未提交时使用当前日期，提交后再作为历史证据。不随批次内每次编辑反复改写。
10. 发布包（plugin / bundle）的版本与 skill 行为版本**分开**管理。

两段式版本、`0.x` 初始开发语义、指纹范围与日期取值是**本规范的治理约定**，非开放标准要求：开放标准仅把 `metadata.version` 作为可选自由字符串；插件市场普遍另用三段式 semver，故发布包版本按第 10 条分开管理。

**建议**配 CI 门禁（gate），至少校验：目录名 = `name`；version 两段式、updated 格式合法；实质内容变更时版本与日期已同步更新。行为指纹必须排除第 8 条列出的治理和纯展示字段，但保留调用策略、工具依赖、默认调用提示词等行为 adapter。若存在 `skill-manifest.json`，再校验其为合法 JSON、最新 changelog 与 `SKILL.md` 版本/日期一致且随行为版本同步。

### 11.2 协作流程

多人协作以 Git 为真源，平台承载分发产物；原始作者、修改过程和评审证据由 Git / PR 保留。

| 变更 | 流程 |
|---|---|
| 正文 / `references/` / `scripts/`（行为面） | PR + 评审 |
| `examples/` 新增样例 | 轻量评审 |
| `evals/` | 与对应行为变更同一 PR |
| `skill-manifest.json`（若存在） | 与对应行为版本同一 PR；单独维护人变更不升行为版本 |
| 发布到平台 | 构建产物上传；真源在 Git |

若仓库维护 skill 的镜像副本（示例目录与发布包并存同一份 skill），镜像**必须**与真源逐字节一致，由门禁校验。

### 11.3 废弃与替代

1. skill 下线或被替代时，**建议**在 `description` 标注 deprecated 并指向替代 skill，保留至少一个发布周期后再移除。
2. 大版本换代采用平级新包（`<name>-v2`）时，旧包按上条处理。

### 11.4 安装与实例变更

安装、覆盖、重命名、迁移或恢复已安装实例时，检查目标运行时发现根和本次涉及的源、市场、备份副本，核对路径、调用名、宿主管理身份、来源与内容关系。发现重复或旧实例时停止自动覆盖、合并或删除，由用户决定处置；不能仅凭展示名判断同一性。

受管实例遵循宿主的修改标记与更新保护；备份放在发现根之外。文件存在与实际加载分别验证。纯源码修订只检查当前包及声明的镜像，不扫描无关运行时。

## 附录 A：可选轻量治理文件

`skill-manifest.json` 是可选且默认不创建的同目录治理文件。只有维护人与简短版本说明确需脱离 Git 随包携带时才创建；它不参与 Skill runtime，不替代 Git、PR 或 release notes，也不应被 `SKILL.md` 正文引用为执行说明。

```json
{
  "maintainer": "BlueSkyXN",
  "changelog": [
    {
      "version": "0.2",
      "date": "2026-07-28",
      "updated_by": "BlueSkyXN, Alice",
      "changes": "description 改为单行事件描述；补充工作流完成条件。"
    },
    {
      "version": "0.1",
      "date": "2026-07-17",
      "updated_by": "BlueSkyXN",
      "changes": "建立首个可执行版本。"
    }
  ]
}
```

存在该文件时，约束保持最小：

1. 顶层只使用 `maintainer` 与 `changelog`；不预设 schema、status、author、license、tag、reviewer、AI 或测试结果字段。
2. `maintainer` 是非空字符串；多人用英文逗号加一个空格分隔，只记录当前人类负责人或稳定团队，并与 `SKILL.md` 的 `metadata.maintainer` 一致。
3. `changelog` 是非空数组，最新行为版本在第一项；每项只含 `version`、`date`、`updated_by`、`changes`。
4. `updated_by` 只记录形成该行为版本的负责人和人类修改人，多人同样用英文逗号加一个空格分隔；不记录 AI、formatter、CI 或自动镜像。最新一项与 `SKILL.md` 的 `metadata.updated_by` 一致。
5. `changes` 是单行非空字符串，用分号分隔少量主要行为变化；不写文件列表、测试命令或开发过程，完整证据仍查 Git 与 PR。
6. `changelog[0]` 的 `version`、`date`、`updated_by` 必须分别等于 `SKILL.md` 的 `metadata.version`、`metadata.updated`、`metadata.updated_by`；顶层 `maintainer` 也必须与 `metadata.maintainer` 一致。
7. 纯排版、镜像同步、纯治理或纯展示字段变更、维护人变更不新增 changelog，也不升级行为版本；改变调用或执行行为的字段按第 11 章处理。
8. `skill-manifest.json` 本身不进入实质内容指纹；该文件存在时，其他行为文件发生实质变化并升级版本，必须同步在 changelog 顶部新增一项。

## 附录 B：内部私有案例材料

**内部私有案例的受限例外**：本节的权限边界规则不把公司内部案例一概排除在包外。只有同时满足下列全部条件时，才**可以**把经过最小化整理的案例材料放入内部私有 Skill 的正文、`references/`、`examples/` 或 `assets/`；这不是对“客户数据”的宽泛放开，也不授权 Agent 自动决定持久化：

1. Skill 的 Git 真源、分发包、安装位置与运行时访问权限均为内部私有，受限于被授权人员；公开仓库、公开插件/市场、公开示例、可外发产物和受众不明的渠道一律视为公开边界。
2. 有权授权该材料的用户或数据责任人已作出**明确、可追溯**的授权；授权记录放在受控的包外位置，至少能核对授权方、来源、批准用途、访问/使用范围，以及适用的有效期或撤销条件。受控审批记录、任务中的明确指令或适用项目规则均可作为证据；不得把“公司内部”或口头默认当作授权。
3. **使用授权与写入 Skill 的持久化决定必须分开。** 在修改文件前，Agent 必须向用户说明拟写入的案例、目标文件与保留字段，并提示至少以下风险：可识别信息、Git/分发包/runtime 副本与未来 Agent 可见范围、日志或输出再传播、公开抽取风险，以及撤销时需处理当前文件、历史记录和已安装副本。随后由用户明确选择“最小化后写入”“进一步脱敏后写入”“仅本次使用不写入”或“不使用”。仅允许读取、分析或本次使用不等于允许持久化；沉默、含糊回答或只有既往授权时，默认不写入。
4. 材料只保留实现获批用途所必需的最小字段、片段和时间范围，并优先使用摘录、汇总、伪名化或脱敏后的表示；来源、版本或受控记录标识必须可追溯，但不把原始材料复制成包内快照。
5. 原始报告、完整附件、原始导出、凭据、访问 token 和连接信息始终包外，并继续由其原有权限系统控制；Skill 只写获得授权后的最小案例材料与取得方式。
6. Skill 的正文、脚本和输出契约必须把对外、公开、跨组织或未获授权的输出规定为脱敏/聚合结果；不得以调试、示例、评测或日志为由泄露可识别客户或个人数据。
7. 任何新增用途、受众、分发渠道、数据字段或跨境/跨组织传递超出原授权范围时，先取得新的明确授权；未经授权不得复制、导出、共享或扩散。

上述例外只改变内部私有 Skill 的最小案例材料落点，不改变密钥、凭据和原始报告必须包外的规则，也不改变公开发布禁止可识别客户或个人数据的规则（见 10.3）。
