# Agent Skill 开发规范

| 项 | 值 |
|---|---|
| 文档 ID | `skill-spec` |
| 版本 | 0.2 |
| 日期 | 2026-07-28 |
| 定位 | 通用 Agent Skill 开发规范：分类、结构、写法、组织、版本与协作 |
| 分发 | **自包含单文件**：执行本文不依赖任何外部文件 |
| 适用对象 | Skill 作者、评审者、AI Agent |

本规范定义 Agent Skill 的分类体系、包结构、`SKILL.md` 写法、多 skill 组织、评测与版本协作规则，适用于任何兼容 [Agent Skills 开放标准](https://agentskills.io) 的运行时（Claude Code、Codex、Copilot CLI、OpenClaw、CodeBuddy、WorkBuddy、Qoder 等）。

条款以三个来源校准，不设立缺乏依据的约定：

1. **开放标准**：Agent Skills 开放标准定义的可移植底座。
2. **平台硬限**：各运行时公开文档中的强制约束。
3. **工程实践**：多平台生产环境 skill 仓库的既有共识。

---

## 1. 如何使用本规范

### 1.1 读者路径

| 你要做的事 | 阅读 |
|---|---|
| 30 秒了解全貌 | 附录 A 一句话备忘 |
| 新建一个 skill | 第 12 章模板起步 + 第 2～6 章 + 第 11 章清单 |
| 个人自用、暂不发布 | 第 12 章模板 + 第 2～6 章；第 8～9 章与 5.4 平台发布注意可暂缓 |
| 评审 skill | 第 10 章禁止清单 + 第 11 章合格清单 |
| 组织多个 skill / 建 router | 第 3、7 章 |
| 定版本、多人协作 | 第 9 章 |
| 生成或校验 skill（AI Agent） | 1.2 节 + 全部「必须 / 禁止」条款 |

本规范分两级适用：**可移植合规**（第 2～6 章与第 10～11 章清单），任何 skill 都适用；**协作治理**（第 9 章与 6.1 治理层字段），多人协作或公开发布时为必须，纯个人自用降为建议。

### 1.2 Agent 执行规则

AI Agent 依据本规范生成或评审 skill 时：

1. 「必须 / 禁止」是硬约束；「建议」默认遵循，偏离时说明理由。
2. 目录结构优先使用第 5 章标准目录；新增顶层目录必须能陈述标准目录覆盖不了的独立职责。
3. 结构按需生长：先判断现有材料单文件是否容纳得下，再决定建目录。
4. 条款冲突时：更具体的条款优先于总述性原则。
5. 「说明 / 理由」性文字不构成新目录或新例外的授权。

### 1.3 用语强度

| 用语 | 含义 |
|---|---|
| **必须** / **禁止** | 违反即不合格 |
| **建议** | 默认遵循；偏离需能说明理由 |
| **可以** | 可选 |

### 1.4 范围

- 本规范管：单个 skill 包与多 skill 组织的设计、结构、写法、评测、版本与协作。
- 本规范不管：Agent / 角色系统设计、中央知识库选型与权限模型、各运行时的内部实现细节。

## 2. 核心模型

### 2.1 Skill 的定义

**Skill 是可触发的工序单元**（process unit）：封装一段可复用的工作流程，由运行时在匹配场景中加载执行。

- 一个 skill = 一个目录 + 一个 `name` + 一个 `SKILL.md` 入口。
- Skill 不是长文百科，不是中央知识库，不是配置开关。

### 2.2 三层加载模型（渐进披露）

Skill 内容按三层加载，各层预算不同。**本规范的全部内容落点规则都由这个模型推导：**

| 层 | 加载时机 | 承载内容 | 预算特征 |
|---|---|---|---|
| L1 发现层 | 运行时发现或列出已启用 skill 时加载；可能受产品门控与上下文预算限制 | `name` + `description` | 极小，与其他 skill 共享预算 |
| L2 执行层 | 触发后整体加载 | `SKILL.md` 正文 | 有限，应精炼 |
| L3 资源层 | 执行中按需读取 | `references/`、`examples/`、`scripts/`、`assets/` | 按需，不占触发预算 |

四条推论：

1. Skill 的能力与适用事件**必须**写进 `description`——它是可移植发现层中表达选择语义的主依据；平台私有调用字段、门控开关、上下文预算与显式调用仍可能影响实际可见性和选择结果。
2. 主工作流**必须**写在正文——L2 是触发后唯一保证加载的内容。
3. 执行中才需要的细节放 L3，正文只留链接与使用时机。
4. 运行时不读的内容与超出包尺度的内容不占任何层：评测材料进 `evals/`，中央知识放包外。

### 2.3 核心原则

1. **Git 为协作真源，平台为发布渠道**：真源（source of truth）在 Git；上传、插件市场上架是发布动作，不是多人共编方式；协同、评审、合并在 Git 完成。
2. **可移植底座 + 平台适配**：以开放标准（`SKILL.md` + `name` / `description` + 渐进披露）为底座；平台私有能力通过各自的扩展落点实现（见 6.1），不污染底座。
3. **结构按需生长**：从单文件开始，材料真实出现后再建目录；**禁止**预建空目录。
4. **引用而非复制**：外部 skill 与中央知识只引用，不复制正文进包。
5. **同一事实只留一份真源**：规则写一处，其余位置引用。

## 3. 分类体系

### 3.1 形态分类

形态描述包的**现状**，不是升级路线图；一个 skill 可以永远停留在单文件形态。

| 形态 | 判定 | 结构特征 |
|---|---|---|
| **单文件**（single-file） | 只需 `SKILL.md` 即可完整执行 | 仅 `SKILL.md` |
| **标准**（standard） | 单文件容纳不下，出现配套文件 | + `references/` / `scripts/` / `examples/` 中任意 |
| **套件**（multi-route） | 一包内多条**同一意图族**路线 | 正文含路线选择；配套目录成型 |
| **群**（fleet） | 数十个独立 skill 的平级组织 | 多包平级 + 可选 router |

判定顺序：先分单包（前三种形态）与多包（群）；单包内再看文件形态与路线数。

术语提示：本规范的「套件」（multi-route）指单包多路线，不同于 Codex 生态中编排 agent 的 suite，也不同于 QoderWork 等产品中打包多个 skill 的角色 plugin——那些属于 agent 编排与分发概念，不是单个 skill 包的形态。

### 3.2 套件规则

1. **必须**仍是一个包：一个 `name`、一个 `SKILL.md`；**禁止**包内嵌套子 `SKILL.md`。
2. **必须**多条路线同属一个意图族；不同意图族的工作流拆为独立 skill。
3. 意图族（intent family）判定：多条路线能被同一条 `description` 自然覆盖、无需用「或」并列互不相干的场景，即属同一意图族；反之应拆为独立 skill。该判定源自三层加载模型——套件的全部路线共用一条发现层描述（见 2.2）。判例：「提取 PDF 文本、填写表单、合并文件，处理 PDF 时使用」属同一意图族（同一对象与场景入口，开放标准的示例 description 即此写法）；「生成周报或初始化数据库」不属（场景互不相干，只能靠「或」并列）。
4. **必须**在正文写清路线选择规则：何种输入或场景走哪条路线。

### 3.3 群规则

1. 群内每个叶子（leaf，即群内单个 skill）独立满足单包规则（第 5～6 章），平级排列。
2. Router（引导 skill）是可选件，不是标配：实践参考线约 30 个以上独立可触发 skill、且入口多样到需要引导时才值得建；叶子数量达数十时才需要两级 router。
3. 规模未达参考线时，**建议**不建 router：靠 `description` 区分 + 文档级地图（README / docs）即可；因产品入口等原因提前建的，须说明理由，且 router 仍须满足 7.2。
4. **禁止**把同一 workflow 拆成 Phase 1…N 伪装成多个独立 skill。

## 4. 内容落点

### 4.1 落点决策

判定问题：**这段材料执行时要不要被 agent 读？何时读？**

| 材料 | 落点 | 对应层 |
|---|---|---|
| 能力与适用事件 | `description` | L1 |
| 主工作流、完成条件、硬禁令 | `SKILL.md` 正文 | L2 |
| 执行时按需查的规则、协议、契约、排查手册 | `references/`（篇幅短则并入正文） | L3 |
| 输入输出样例、正反例、长支路演示 | `examples/` | L3 |
| 可靠可复跑的命令与脚本 | `scripts/` | L3 |
| 输出模板、静态资源 | `assets/` | L3 |
| 触发 / 质量回归材料 | `evals/` | 不加载 |
| 需要脱离 Git 随包携带的维护人与轻量 changelog | `skill-manifest.json` | 不加载；可选，默认不创建 |
| 公司内部、经明确授权且最小化整理的案例材料 | 仅限内部私有 Skill 的正文或相应资源目录；具体边界见 4.3 | 按实际读取时机 |
| 大体量 / 多包共享 / 有权限边界的语料 | 包外（知识库、MCP（Model Context Protocol）服务、独立仓库） | 包外 |
| 外部 skill 的工序 | 包外引用：写清何时用、怎么调 | 包外 |

### 4.2 资料目录分工

```text
references = 怎么做对（执行说明）
examples   = 长什么样（示范）
evals      = 测过了吗（回归；运行时不读）
```

同一事实只留一份真源：硬性规则写在正文或 `references/`；`examples/` 只做示范；`evals/` 只写可观察断言。三者都可以没有。

### 4.3 包外原则

材料命中任一条件即放包外：

1. 体积大（数千 token 以上）。
2. 更新节奏独立于 skill 流程。
3. 被多个 skill 共享。
4. 存在权限或密级差异。

规则：

- 包内**可以**写「怎么查」：用什么服务或命令、典型查询、结果怎么用；直接写进正文或 `references/`，不需要专用配置格式。
- **禁止**把中央知识正文复制进包内；**禁止**建立包内快照目录形成第二真源（真源漂移的根源）。
- 引用外部 skill 时：用稳定名称 + 写清前置条件与失败降级；**禁止**复制对方正文。

**内部私有案例的受限例外**：本节的权限边界规则不把公司内部案例一概排除在包外。只有同时满足下列全部条件时，才**可以**把经过最小化整理的案例材料放入内部私有 Skill 的正文、`references/`、`examples/` 或 `assets/`；这不是对“客户数据”的宽泛放开，也不授权 Agent 自动决定持久化：

1. Skill 的 Git 真源、分发包、安装位置与运行时访问权限均为内部私有，受限于被授权人员；公开仓库、公开插件/市场、公开示例、可外发产物和受众不明的渠道一律视为公开边界。
2. 有权授权该材料的用户或数据责任人已作出**明确、可追溯**的授权；授权记录放在受控的包外位置，至少能核对授权方、来源、批准用途、访问/使用范围，以及适用的有效期或撤销条件。受控审批记录、任务中的明确指令或适用项目规则均可作为证据；不得把“公司内部”或口头默认当作授权。
3. **使用授权与写入 Skill 的持久化决定必须分开。** 在修改文件前，Agent 必须向用户说明拟写入的案例、目标文件与保留字段，并提示至少以下风险：可识别信息、Git/分发包/runtime 副本与未来 Agent 可见范围、日志或输出再传播、公开抽取风险，以及撤销时需处理当前文件、历史记录和已安装副本。随后由用户明确选择“最小化后写入”“进一步脱敏后写入”“仅本次使用不写入”或“不使用”。仅允许读取、分析或本次使用不等于允许持久化；沉默、含糊回答或只有既往授权时，默认不写入。
4. 材料只保留实现获批用途所必需的最小字段、片段和时间范围，并优先使用摘录、汇总、伪名化或脱敏后的表示；来源、版本或受控记录标识必须可追溯，但不把原始材料复制成包内快照。
5. 原始报告、完整附件、原始导出、凭据、访问 token 和连接信息始终包外，并继续由其原有权限系统控制；Skill 只写获得授权后的最小案例材料与取得方式。
6. Skill 的正文、脚本和输出契约必须把对外、公开、跨组织或未获授权的输出规定为脱敏/聚合结果；不得以调试、示例、评测或日志为由泄露可识别客户或个人数据。
7. 任何新增用途、受众、分发渠道、数据字段或跨境/跨组织传递超出原授权范围时，先取得新的明确授权；未经授权不得复制、导出、共享或扩散。

上述例外只改变内部私有 Skill 的最小案例材料落点，不改变密钥、凭据和原始报告必须包外的规则，也不改变公开发布禁止可识别客户或个人数据的规则（见 5.4、10、11.3）。

## 5. 包结构

### 5.1 标准目录

```text
<skill-id>/                  # 目录名 = name
├── SKILL.md                 # 必须：唯一入口
├── skill-manifest.json      # 可选、默认不建：仅在治理信息需脱离 Git 随包携带时使用
├── references/              # 可选：按需读的执行说明
├── examples/                # 可选：样例与演示
├── scripts/                 # 可选：可执行辅助
├── assets/                  # 可选：模板与静态资源
├── <平台 adapter>            # 可选：按目标平台要求放置（见 6.1）
├── evals/                   # 可选：回归材料（运行时不读）
└── README.md / LICENSE*     # 可选：分发说明，不承载工序
```

目录出处：`references/`、`scripts/`、`assets/` 是开放标准点名的推荐可选目录；`skill-manifest.json`、`examples/`、`evals/` 与平台 adapter 为本规范的工程补充，落在开放标准「允许额外文件与目录」的范围内。

结构规则：

1. **必须**：有且仅有一个 `SKILL.md`；目录名与 `name` 一致。
2. **禁止**：包内第二个 `SKILL.md`（含子目录嵌套）——那是两个 skill，应拆分。
3. **禁止**：预建空目录。
4. **禁止**：包内版本目录（`v2/`、`v3/`）；版本换代走版本契约（第 9 章）或开平级新包（`<name>-v2`）。
5. **建议**：内容优先落入标准目录；新增顶层目录须有标准目录覆盖不了的独立职责，并在评审中说明。
6. 历史包若有说明文件平铺在包根，不判不合格，但新建包不采用；引入外部包同理，标准目录之外的既有目录随大改收敛。
7. `skill-manifest.json` 只承载治理信息，**禁止**承载 Skill 工作流、工具权限、调用控制或平台 UI 配置；它是可选 sidecar，默认不创建。只有维护人与简短版本说明确需脱离 Git 随包携带时才使用，公开发布或多人协作本身不构成创建理由。

### 5.2 生长规则

1. 从单文件 `SKILL.md` 开始。
2. 某类材料真实出现时才建对应目录：执行说明成型 → `references/`；样例沉淀 → `examples/`；命令固化 → `scripts/`；模板复用 → `assets/`；回归需求出现 → `evals/`；治理信息确需脱离 Git 随包携带 → `skill-manifest.json`；面向特定平台发布 → adapter。
3. 没有新材料就停留在当前形态；形态只描述现状，不构成升级压力。

### 5.3 命名规则

**必须**：

1. 目录名 = `name`：全小写英文，词间用连字符，不含空格、大写与下划线（如 `weekly-report`、`pdf-extract`），长度不超过 64 字符（开放标准上限）；形式化定义为正则 `^[a-z0-9]+(?:-[a-z0-9]+)*$`（kebab-case）。
2. 入口文件名固定为 `SKILL.md`。

部分产品 UI 允许本地化命名（如中文 skill 名、展示名）或省略 `name` 回退目录名，均属产品私有行为，不构成可移植包的例外：跨运行时分发仍按上述规则命名，UI 展示名放平台扩展字段（见 6.1）。中文意图的命名路径：按意图取达意的英文名（「周报生成」→ `weekly-report`，「PRD 撰写」→ `prd-writer`），中文能力与适用事件写进 `description`，中文展示名放平台扩展字段——发现与选择主要靠 `description` 而非 `name`（见 6.2），英文命名不影响中文场景的选择。

**建议**：

1. 群内用前缀分域（如 `dev-` / `data-` / `office-`），兼容各运行时的扁平发现模型。
2. `references/` 用语义名平铺（`output-contract.md`、`troubleshooting.md`）；同主题文件多时最多一层子目录。
3. `examples/` 用语义名；正反例以 good / bad 标注（前后缀均可）；演示序列可用 `NN-<slug>.*`；不用日期做文件名——样例是稳定资产，不是日志。
4. `scripts/` 用动宾式命名（`validate_output.py`）；公共模块命名不限。

### 5.4 发布与提交

| 内容 | 处置 |
|---|---|
| `SKILL.md`、`references/`、`examples/`、`scripts/`、`assets/`、adapter、分发说明文件 | 随包发布 |
| `skill-manifest.json` | 若已按需创建则随包发布；默认不存在 |
| `evals/` | 建议随包，便于消费方回归；非运行时依赖 |
| 生成物与系统垃圾（缓存、`.DS_Store` 等） | **禁止**提交 |
| 密钥、凭据、访问 token、原始报告、完整附件或原始导出 | **禁止**出现在任何 Skill 包内 |
| 公开仓库、公开插件/市场、公开示例、可外发产物或受众不明的包 | **禁止**出现可识别的个人或客户数据，以及内网地址 |
| 内部私有 Skill 的最小化案例材料 | **可以**随内部私有 Git 真源和受限分发提交/安装，但必须逐项满足 4.3 的明确授权、写入前风险提醒与人工持久化决定、用途/范围、最小必要、来源可追溯、包外原件与对外脱敏要求 |

安全规则：

1. 脚本行为**必须**与正文声明一致；**禁止**执行正文未声明的网络外发、数据上传或删除性操作。
2. 正文与 `description` **禁止**指示 agent 绕过运行时的权限确认或安全机制。
3. **建议**引入第三方 skill 前通读其 `SKILL.md` 与脚本：skill 同时是提示词与可执行代码，应按不可信代码对待。

平台发布注意：各平台对文件类型与包体积有硬限（如仅接受文本文件、单包 50MB 级），发布前核对目标平台文档；打包由脚本完成，真源始终在 Git。

将内部私有 Skill 转为公开发布、公开示例或可外发产物前，必须移除全部可识别个人/客户数据和内部访问细节，并重新检查每个引用、示例、评测、日志与生成物；原有内部授权不自动构成公开授权。

### 5.5 多实例身份与重复安装检查

创建、导入、安装、重命名、迁移、从备份恢复或更新 Skill 前后，**必须**扫描目标运行时的实际发现根以及已知源目录、市场安装目录和备份目录，建立实例表；只检查计划写入的目标目录是否存在，不足以排除重复安装。

每个实例至少记录以下身份维度：

| 维度 | 证据 | 含义 |
|---|---|---|
| 文件系统实例 | 绝对路径、是否 symlink、是否位于运行时发现根 | 判断它是否可能参与当前运行时发现 |
| Skill 逻辑身份 | `SKILL.md.name` | 可移植调用与选择身份；同一发现根内重复时可能冲突 |
| 平台管理身份 | 市场或宿主 metadata 中的 `skillId`、`source` 等 | 判断是否为同一 marketplace / enterprise 安装，不得用目录名代替 |
| 来源身份 | repo、ref / revision、源内子路径或市场来源 | 判断真源、更新链和是否允许覆盖 |
| 版本与内容关系 | Skill 行为版本、包版本、文件清单以及 hash / `diff` | 区分相同镜像、旧副本、分叉修改和仅重命名副本 |
| 展示信息 | `display_name` 或平台 UI 字段 | 只用于识别 UI 冲突，**不得**单独作为 Skill 身份 |

处置规则：

1. 同一发现根内存在相同 `name` 的多个目录，或不同平台管理 ID 映射到同一调用名时，视为重复发现候选；在身份收敛前停止自动安装、覆盖或删除，并报告全部路径和来源。
2. 同一平台 `skillId` 出现在不同目录时优先按同一受管身份调查；相同内容位于发现根之外的 Git 真源或备份目录时，不算运行时重复，但必须明确哪一份是真源、哪一份只是镜像。
3. 相同 `display_name` 不足以证明是同一个 Skill；相同 `name` 也不足以证明内容或来源相同。必须结合平台 ID、来源和内容比较下结论。
4. 重命名前同时扫描旧 `name` 与新 `name`；重命名后重新扫描。仍有旧实例时只能报告“指定实例已重命名”，不得声称所有运行时实例已完成迁移。
5. 带 `_skillhub_meta.json`、`_knot_meta.json` 或其他宿主管理 metadata 的实例先按市场 / enterprise 包处理。未经明确授权不得修改、删除或用本地副本覆盖；确需修改时遵循宿主的 `userModified`、更新保护和版本规则。
6. 不因发现重复而静默合并或删除。由用户决定保留、迁移、停用或删除哪个实例；备份优先放在运行时发现根之外，避免备份本身再次被发现。
7. 文件系统扫描只能证明实例存在；实际加载、去重优先级、UI 展示和调用结果必须在重载或新会话中另行验证并分别报告。

## 6. SKILL.md 写法

### 6.1 Frontmatter

Frontmatter 指 `SKILL.md` 开头两条 `---` 之间的元信息区（YAML 格式），运行时靠它发现与识别 skill。部分产品在 UI 中代填此区。只求可移植发现的个人 Skill 最少写 `name` 与 `description`；需要多人协作、公开发布或明确维护责任时，使用下面的治理型模板：

```yaml
---
name: <与目录名一致>
description: <做什么，以及适用于什么事件、任务或输入状态；必须写成单个物理行>
metadata:
  version: "0.1"          # 新 Skill 的首个实质状态；两段式字符串，契约见第 9 章
  updated: "YYYY-MM-DD"
  maintainer: "<当前人类负责人或稳定团队>"
  updated_by: "<形成当前行为版本的人类修改人>"
---
```

这里的 `"0.1"` 表示**新建 Skill 的初始行为版本**，不是本文档的版本。已有 Skill 应保留并按第 9 章推进自己的版本，不能因为复制模板而改回 `0.1`。多人字段使用英文逗号加一个空格分隔，例如 `"Alice, Bob"`。

字段分三级：

| 级 | 字段 | 强度 |
|---|---|---|
| 可移植底座 | `name`、`description` | **必须**（开放标准要求） |
| 生命周期治理 | `metadata.version`、`metadata.updated` | 多人协作或公开发布场景**必须**；纯个人自用**建议** |
| 责任治理 | `metadata.maintainer`、`metadata.updated_by` | 多人协作或公开发布场景**建议**；需要随文件明确责任时填写 |
| 平台扩展 | UI、调用、工具与运行时私有字段 | 仅面向已验证的目标平台写；默认省略 |

字段规则：

1. `name`：**必须**与目录名一致。
2. `description`：**必须**；必须写在 `description:` 所在的单个物理行，不使用 `>`、`>-`、`|`、`|-` 等多行 YAML scalar；写法规则见 6.2。
3. `metadata.version`：行为版本，两段式字符串；契约见第 9 章。
4. `metadata.updated`：`YYYY-MM-DD`，取最后一次实质变更日期。
5. `metadata.maintainer`：当前对 Skill 负责的人类或稳定团队；多人时使用英文逗号加一个空格分隔。维护责任转移只更新该字段，不因此升级行为版本。
6. `metadata.updated_by`：形成当前行为版本并对结果负责的人类修改人；多人格式同上。AI、formatter、CI、自动镜像不署名；若 AI 参与修改，记录提出、审阅并接受该行为版本的人类负责人和修改人。
7. 不设置 `author`：原始作者与历次贡献者由 Git history / PR 保留，避免把永久作者、当前负责人和当前版本修改人混成一个字段。
8. 本规范默认不在每个 `SKILL.md` 重复写 `license`，随仓库或 plugin 发布时由 package/repository license 统一覆盖；独立拆包分发时必须在包内另行提供明确许可。`compatibility` 等开放标准可选字段可以按需使用。私有属性放 `metadata` 键下；顶层未知字段被忽略还是拒绝，跨运行时行为未经验证，混投多平台前先做冒烟验证。
9. `disable-model-invocation` 是可选的平台调用字段：默认省略；只有 Skill 必须由用户显式调用时才写 `true`，不写 `false`。它不禁用 Skill，也不控制工具权限。Codex 的对等策略写在 `agents/openai.yaml`：`policy.allow_implicit_invocation: false`。
10. `display_name` 是 **WorkBuddy-only** 的可选顶层 UI 字段：默认省略；仅在明确面向 WorkBuddy 且需要与 `name` 不同的用户展示名时写非空字符串。它不替代 `name`，不参与 Skill 发现或模型选择，也不单独升级行为版本。WorkBuddy 5.2.6 loader 还兼容 `display-name`，但本规范只写 `display_name`；camelCase `displayName` 属于 WorkBuddy Expert / Plugin 等其他层，不作为 Skill frontmatter 字段。

平台扩展的常见落点（互不污染，按目标平台选用）：

| 扩展方式 | 典型平台 | 形态 |
|---|---|---|
| Sidecar 文件 | Codex | `agents/openai.yaml`；Skill UI 名写 `interface.display_name`，不写进 `SKILL.md` |
| Frontmatter 运行时字段 | Claude Code、CodeBuddy | `allowed-tools`、`context` 等 |
| Frontmatter 厂商命名空间 | OpenClaw | `metadata.openclaw.*` |
| Frontmatter 产品字段 | WorkBuddy、QoderWork | WorkBuddy Skill 的 `display_name`、非空 `allowed-tools` 与 `disable-model-invocation` 有当前 loader 证据；`license` 与裸 `disable` 仅为 builtin 观察字段。QoderWork 有自己的双语展示字段。具体语义只在对应平台证据中定义 |

第四类是无命名空间的顶层私有字段，跨运行时兼容性最弱（见上方字段规则 8、10），仅面向对应产品发布时保留。

展示名必须按平台落位，不得把相同拼写当作跨平台字段：

| 平台 | Skill 展示名 | 规则边界 |
|---|---|---|
| OpenAI Codex / ChatGPT | `agents/openai.yaml` → `interface.display_name` | sidecar 可选；一旦创建，`interface.display_name` 与 `interface.short_description` 必须是非空字符串。`SKILL.md metadata` 不配置 OpenAI UI |
| Claude Code | `SKILL.md` → `name` | 当前官方 Skill frontmatter 没有独立 display-name 字段；个人/项目 Skill 的显式命令通常来自目录，Plugin Skill 的 `name` 还会影响命令末段。为保持可移植性，仍使用目录名 = `name`，不拿它做本地化 UI 文案 |
| WorkBuddy 5.2.6 | `SKILL.md` → `display_name` | 仅 WorkBuddy 有效；loader 支持但 bundled Skill 文档未列出，15 个顶层 builtin 也未使用。使用字符串并默认省略；`display-name` 只作兼容别名，`displayName` 不属于这一层 |

OpenAI adapter 示例：

```yaml
# agents/openai.yaml
interface:
  display_name: "生产环境部署"
  short_description: "执行经过审批的正式生产部署"
```

WorkBuddy adapter 示例（以下 `display_name` 只对 WorkBuddy 生效）：

```yaml
---
name: production-deploy
display_name: "生产环境部署"
description: 执行生产环境部署，适用于发布审批、构建验证和部署前检查已经完成的正式交付任务。
metadata:
  version: "0.1"
  updated: "2026-07-28"
  maintainer: "Alice"
  updated_by: "Alice"
---
```

显式调用示例（仅目标平台支持时使用）：

```yaml
---
name: production-deploy
description: 执行生产环境部署，适用于发布审批、构建验证和部署前检查已经完成的正式交付任务。
disable-model-invocation: true
metadata:
  version: "0.1"
  updated: "2026-07-28"
  maintainer: "Alice"
  updated_by: "Alice"
---
```

### 6.2 能力与适用事件描述（description）

在可移植层，`description` 是自动发现与选择的主依据。它应描述 Skill 能处理的事情及适用的客观事件、任务或输入状态，而不是猜测用户会说出的词句。它是必要条件，但不能单独保证 Skill 会被自动选中：运行时私有调用字段、启用或权限门控、上下文预算与显式调用都可能影响实际可见性和选择结果。这些平台扩展不可移植，也不改变以下写法规则：

1. **必须**同时包含「做什么」与「适用于什么事件、任务或输入状态」；这些信息**禁止**只写在正文。
2. **禁止**把用户可能说出的关键词、口令、示例问法或固定句式当作主要定义；应描述客观任务语义，例如输入材料、目标动作、处理对象和所处状态。
3. **必须**保持单行；建议使用一个紧凑句子，必要时用分号组织多个相邻适用事件。
4. 默认不写「何时不用」；只有在两个相邻 Skill 的职责确实重叠、单靠正向事件边界仍无法区分时，才增加最小必要的排除说明。
5. 长度：**建议** 100～200 字；可移植上限 1024 字符；部分运行时的列表展示另有更短的截断阈值，关键信息前置。
6. **建议**语言与目标使用环境一致；本规范下的办公类 Skill（包括 `office-*`，以及以文档、表格、演示、PDF、周报、邮件、飞书等办公材料或流程为主要对象的 Skill）其 `description` **必须优先使用中文**。只有目标用户或发布环境明确以其他语言为主时才例外；文件扩展名、产品名、API、配置键和代码标识符保留原文。
7. 上述办公类中文规则是本规范的项目约定，不是 Agent Skills 开放标准或 Codex、Claude Code、WorkBuddy Skill 层的语言硬限制；上游只约束 `description` 的存在、长度或“能力 + 适用情境”等语义，不规定必须使用英文或中文。
8. 选择问题的修正路径：未被选中 → 补齐遗漏的事件、输入状态、处理对象或目标动作；被错误选中 → 收窄正向任务边界，只有仍无法区分时才增加排除说明。

### 6.3 正文

硬要求四条：

1. 主工作流**必须**写在正文；**禁止**正文只剩链接壳。
2. 关键路线**必须**有可观察完成条件（命令、产物、检查项）。
3. 套件**必须**写清路线选择。
4. 相对链接**必须**全部可达；**禁止**预链不存在的文件。

**建议**骨架（非强制）：

```markdown
# <标题>
## 适用事件与输入
## 前置检查
## 工作流          # 每条路线附完成条件
## 输出与完成条件
## 异常与禁止
## 参考            # 只链真实存在的文件与外部 skill
```

正文保持精炼（数百行以内），细节移入 `references/`。

### 6.4 轻量治理文件（skill-manifest.json）

`skill-manifest.json` 是可选且默认不创建的同目录治理文件。只有维护人与简短版本说明确需脱离 Git 随包携带时才创建；它不参与 Skill runtime，不替代 Git、PR 或 release notes，也不应被 `SKILL.md` 正文引用为执行说明。

```json
{
  "maintainer": "BlueSkyXN",
  "changelog": [
    {
      "version": "0.2",
      "date": "2026-07-28",
      "updated_by": "BlueSkyXN, Alice",
      "changes": "description 改为单行事件描述；补充 WorkBuddy 字段边界。"
    },
    {
      "version": "0.1",
      "date": "2026-07-17",
      "updated_by": "BlueSkyXN",
      "changes": "建立首个可执行版本。"
    }
  ]
}
```

存在该文件时，约束保持最小：

1. 顶层只使用 `maintainer` 与 `changelog`；不预设 schema、status、author、license、tag、reviewer、AI 或测试结果字段。
2. `maintainer` 是非空字符串；多人用英文逗号加一个空格分隔，只记录当前人类负责人或稳定团队，并与 `SKILL.md` 的 `metadata.maintainer` 一致。
3. `changelog` 是非空数组，最新行为版本在第一项；每项只含 `version`、`date`、`updated_by`、`changes`。
4. `updated_by` 只记录形成该行为版本的负责人和人类修改人，多人同样用英文逗号加一个空格分隔；不记录 AI、formatter、CI 或自动镜像。最新一项与 `SKILL.md` 的 `metadata.updated_by` 一致。
5. `changes` 是单行非空字符串，用分号分隔少量主要行为变化；不写文件列表、测试命令或开发过程，完整证据仍查 Git 与 PR。
6. `changelog[0]` 的 `version`、`date`、`updated_by` 必须分别等于 `SKILL.md` 的 `metadata.version`、`metadata.updated`、`metadata.updated_by`；顶层 `maintainer` 也必须与 `metadata.maintainer` 一致。
7. 纯排版、镜像同步、metadata-only 或维护人变更不新增 changelog，也不升级行为版本。
8. `skill-manifest.json` 本身不进入实质内容指纹；该文件存在时，其他行为文件发生实质变化并升级版本，必须同步在 changelog 顶部新增一项。

## 7. 多 Skill 组织

### 7.1 布局

```text
skills/
  <router>/           # 可选引导包，本身是合法单包
  leaf-a/             # 每个叶子独立满足第 5～6 章
  leaf-b/
  …
```

平级目录 + 前缀分域；文档级地图放 README / docs，不占运行时。

### 7.2 Router 规则

1. Router **只选路**：意图识别 → 路由表 → 交给目标 skill 执行。
2. **禁止**复制叶子正文；**禁止**在用户要结果时只指路不执行。
3. 路由表**建议**包含：条件、目标 skill、选择原因；外部前置（登录态、服务可用性）单独列出。

### 7.3 Skill 间调用协议

群内一个 skill 调用另一个时，调用方正文写清：

```markdown
当 <条件>：使用 `<skill-name>`
- 传入：…
- 期望返回：…
- 返回后本 skill 继续：…
```

## 8. 评测（evals）

1. 只回答两个问题：**该不该触发**（trigger）、**结果过不过**（quality）。
2. 运行时不读；读者是作者与 CI。
3. 形态自由：json / yaml / md 均可。**建议**至少覆盖「应触发 / 不应触发」两类样本；质量断言写可观察要点与禁令，不复制正文规则。
4. 出现回归需求时再建（`description` 大改、发生过误触 / 漏触、完成条件变更）；**禁止**预建空 `evals/`；**禁止**把日常操作步骤写进 evals 替代正文。

## 9. 版本与协作

### 9.1 版本契约

1. `metadata.version` 是**两段式字符串**（`主.次`，字符串序列而非十进制数），首个实质状态为 `"0.1"`。
2. 主段仍为 `0` 时表示 Skill 处于初始开发或未声明稳定契约；下一次实质状态统一递增次段，例如 `0.1 -> 0.2`、`0.9 -> 0.10`。此阶段即使调整调用名、输入输出或脚本 CLI，也不自动跳到 `1.0`。
3. `1.0` 表示由负责人明确声明首个稳定公开契约，不表示“改动很大”或“质量提升很多”；未作稳定性决定、尚未发布或未被外部消费的 Skill 不得只因一次不兼容修改自动升到 `1.0`。
4. 已进入 `1.x` 及以上稳定阶段后，向后兼容的实质变化递增次段（`1.0 -> 1.1`），破坏公开调用名、必需输入输出契约、产物 schema、脚本 CLI、核心默认流程或其他 Skill 消费契约时递增主段并归零（`1.4 -> 2.0`）。
5. **同一未发布修改批次只升版一次**：短时间内的连续编辑、同一任务中的多轮修订、同一 PR 内的多个 commit、review 后继续收紧，以及文档/实现尚未形成新发布基线前的调整，都合并为一个实质状态。禁止每修改一次就叠加一个小版本。
6. 只有前一版本已经发布、合并为正式基线或被外部消费后，后续新的实质变化才开始下一次升版。时间间隔短本身不要求连续升版，发布/基线边界才决定是否形成新版本。
7. 纯排版、拼写、镜像同步、metadata-only、测试记录或维护人调整不升行为版本。同一批次最终若没有实质行为变化，也不升版。
8. **实质内容**（版本指纹范围）= 正文（不含治理与纯 UI metadata）+ `references/` + `scripts/` + `assets/` + `examples/` + 平台 adapter 中会改变调用、工具、依赖或执行行为的字段。`skill-manifest.json`、`README*`、`LICENSE*`、`evals/`、系统垃圾、治理字段、WorkBuddy `display_name`，以及 OpenAI `interface.display_name` / `short_description` / 图标 / 品牌色等纯展示字段不算实质变更；`policy.allow_implicit_invocation`、工具依赖、`default_prompt` 等会改变使用方式的 adapter 字段仍计入行为版本。
9. `metadata.updated` 取该实质修改批次形成最终状态的 Git committer date（`YYYY-MM-DD`），不随批次内每次编辑反复改写。
10. 发布包（plugin / bundle）的版本与 skill 行为版本**分开**管理。

两段式版本、`0.x` 初始开发语义、指纹范围与日期取值是**本规范的治理约定**，非开放标准要求：开放标准仅把 `metadata.version` 作为可选自由字符串；插件市场普遍另用三段式 semver，故发布包版本按第 10 条分开管理。

**建议**配 CI 门禁（gate），至少校验：目录名 = `name`；version 两段式、updated 格式合法；实质内容变更时版本与日期已同步更新。行为指纹必须排除第 8 条列出的治理和纯展示字段，但保留调用策略、工具依赖、`default_prompt` 等行为 adapter。若存在 `skill-manifest.json`，再校验其为合法 JSON、最新 changelog 与 `SKILL.md` 版本/日期一致且随行为版本同步。

### 9.2 协作流程

| 变更 | 流程 |
|---|---|
| 正文 / `references/` / `scripts/`（行为面） | PR + 评审 |
| `examples/` 新增样例 | 轻量评审 |
| `evals/` | 与对应行为变更同一 PR |
| `skill-manifest.json`（若存在） | 与对应行为版本同一 PR；单独维护人变更不升行为版本 |
| 发布到平台 | 构建产物上传；真源在 Git |

若仓库维护 skill 的镜像副本（示例目录与发布包并存同一份 skill），镜像**必须**与真源逐字节一致，由门禁校验。

### 9.3 废弃与替代

1. skill 下线或被替代时，**建议**在 `description` 标注 deprecated 并指向替代 skill，保留至少一个发布周期后再移除。
2. 大版本换代采用平级新包（`<name>-v2`）时，旧包按上条处理。

## 10. 禁止清单

1. 包内第二个 `SKILL.md`；子目录嵌套 skill。
2. 预建空目录。
3. 无独立职责、与标准目录语义重叠的自造顶层目录。
4. 正文断链；预链不存在的路径。
5. 能力或适用事件只写正文、不进 `description`；或用关键词、口令和示例问法代替任务语义。
6. 正文空心化：主工作流不在 `SKILL.md`。
7. 复制外部 skill 或中央知识正文进包；包内快照第二真源。
8. Router 复制叶子正文；用户要结果时只指路不执行。
9. 套件混入不同意图族的工作流；把同一工作流的 Phase 拆成多个 skill 虚增数量。
10. 把 evals 当运行时手册；硬性规则只写在 examples。
11. 提交生成物、系统垃圾、密钥、凭据、访问 token、原始报告或完整原始导出；在公开边界提交可识别个人/客户数据或内网地址；或在内部私有 Skill 中未先提示持久化风险、未取得明确人工写入决定，或未满足 4.3 其他条件便收录案例材料。
12. 脚本执行正文未声明的外发或删除操作；指示 agent 绕过运行时安全确认。
13. 安装、重命名或更新时只检查目标目录，不扫描同一运行时的其他实例；把 `display_name` 当唯一身份；发现重复后静默覆盖、合并或删除。

## 11. 合格清单

### 11.1 所有单包

- [ ] 目录名 = `name` = kebab-case；有且仅有一个 `SKILL.md`
- [ ] 顶层目录符合 5.1（新增目录有职责说明）
- [ ] `description` 为单行，含做什么 + 适用事件/任务/输入状态，未用关键词或示例问法代替任务语义
- [ ] 主工作流在正文且有可观察完成条件
- [ ] 无断链；无空目录；无生成物、密钥、凭据、访问 token、原始报告或完整原始导出
- [ ] 脚本行为与正文声明一致
- [ ] 外部依赖与中央知识只引用不复制
- [ ] 涉及安装、重命名、迁移、恢复或更新时，已扫描实际发现根和已知源 / 市场 / 备份目录，并按路径、`name`、平台 ID、来源和内容关系建立实例表
- [ ] 没有把 `display_name` 当作 Skill 身份；发现重复或旧 ID 残留时已停止静默覆盖 / 删除，并分别报告文件存在与运行时加载证据

### 11.2 内部私有含授权案例追加

- [ ] 案例仅位于内部私有 Git 真源、受限分发包、安装位置和运行时；没有复制到公开仓库、公开插件/市场、公开示例、可外发产物或受众不明的渠道
- [ ] 每份案例都有包外、可追溯的用户或数据责任人明确授权，并核对了授权方、来源、批准用途、访问/使用范围与有效期或撤销条件
- [ ] 写入前已向用户列明拟写入案例、目标文件、保留字段和持久化/传播/撤销风险，并取得“最小化后写入”或“进一步脱敏后写入”的明确人工决定；仅本次使用、沉默或含糊回答均未触发写入
- [ ] 每份案例只保留获批用途所需的最小字段、片段和时间范围；来源/版本或受控记录标识可追溯，且没有建立原始材料快照
- [ ] 原始报告、完整附件、原始导出、凭据、访问 token 和连接信息仍在包外并受原权限系统控制
- [ ] 正文、脚本、示例、评测、日志和输出契约均禁止向公开、外部、跨组织或未获授权的受众输出可识别个人/客户数据；这类输出只使用脱敏或聚合结果
- [ ] 未把原授权延伸到新增用途、受众、分发渠道、字段或跨境/跨组织传递；任何扩展均已取得新的明确授权

### 11.3 多人协作 / 公开发布追加

- [ ] `metadata.version` / `metadata.updated` 存在且合法（配了门禁则门禁通过）
- [ ] 需要随文件明确维护责任时，`metadata.maintainer` / `metadata.updated_by` 已填写，且只记录人类负责人和当前行为版本修改人
- [ ] 展示名按目标平台落位：Codex 使用 `agents/openai.yaml.interface.display_name`；WorkBuddy 才在 `SKILL.md` 写可选 `display_name`；Claude Code 不虚构独立 display-name 字段
- [ ] WorkBuddy `display_name` 为非空字符串、默认省略且未替代 `name` / `description`；未写兼容别名 `display-name` 或其他层的 camelCase `displayName`
- [ ] 默认未为了形式创建 `skill-manifest.json`；若确需让治理信息脱离 Git 随包携带，则文件结构轻量，最新 changelog 的 version/date/updated_by 与 `SKILL.md` 一致
- [ ] 若存在 `skill-manifest.json`，`maintainer` / `updated_by` 只记录负责人和人类修改人，`changes` 是单行行为摘要
- [ ] 公开仓库、公开插件/市场、公开示例和可外发产物均不含可识别个人/客户数据、内网地址、原始案例材料、凭据或访问 token；内部私有授权不视为公开授权

### 11.4 套件追加

- [ ] 多路线同一意图族；正文有路线选择
- [ ] 无嵌套子 skill

### 11.5 群追加

- [ ] 叶子平级、各自独立合格；router（若有）只选路
- [ ] 规模未到参考线时未建 router（提前建的有理由说明）
